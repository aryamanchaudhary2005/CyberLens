# Known limitations

This is a current implementation summary. Runtime validation status is separately recorded in [test-results.md](test-results.md).

- CyberLens remains a local, single-workspace academic demonstrator, not a public-production deployment. Live Compose use is a local operations exercise and secure cookies require an HTTPS termination layer.
- No multi-tenant isolation, external secret manager, HA database/Redis setup, distributed tracing backend, alert delivery, backup retention policy, or disaster-recovery objective is provided.
- The operations metrics endpoint returns an in-process/request and current queue/provider snapshot, not a durable time-series store. The benchmark captures finite run measurements and is not a production load generator.
- Benchmark measurements are hardware/configuration-specific. No calibrated performance targets or numeric SLOs are defined. The benchmark writes five investigation records and five report snapshots per successful run.
- Provider behavior varies with public data, quota, credentials, service availability, and account tier. Demo scenarios are synthetic and deterministic in content; timestamps, record IDs, generated report times, and performance observations vary by run.
- XposedOrNot's community lookup is disabled by default, limited by the provider to personal/low-volume use and 2 requests/second, 25/hour, and 100/day per IP. Its dataset differs from HIBP, and no cross-provider coverage guarantee exists. The local Redis counter covers one shared CyberLens deployment, not other deployments behind the same egress IP. No live XposedOrNot lookup or current upstream quota behavior has been validated; use only where permitted by the provider's current terms.
- Spamhaus DROP is a narrow advisory list, not general IP reputation or a safety verdict. Refresh is limited locally to once per 24-hour minimum and depends on the fixed official endpoints; stale, failed, or missing snapshots produce unknown coverage. The automated parser expects the documented JSON-lines records and terminal metadata row; a changed upstream schema requires a parser update. No live Spamhaus request or PostgreSQL service migration was run for Module 24.
- CINS Army is a public exact-IP list, not full CINS scoring or a detailed reputation feed. It has no per-indicator score, attack category, report count, first-seen, or publication timestamp in the text file. CyberLens defaults to a 24-hour refresh interval; this is local configuration, not provider publication frequency. A match is a review candidate, and a no-match only describes the saved snapshot. Stale/failed refreshes are unknown; a later absence is not proof of remediation. The feed can change format and requires parser maintenance. No live CINS refresh or PostgreSQL service migration has been run in this workspace.
- OpenPhish community feed use is opt-in and disabled by default. Current provider terms restrict the community dataset to permitted personal/research use; organizational business/security operations and third-party disclosure require prior written permission. Without separately configured provider permission, the backend restricts the Live workspace to one configured owner while its feed data remains stored. Operator acknowledgement does not grant rights. Matching preserves exact URL path, query, fragment, and encoding; old URL assets remain ineligible for direct matching until explicitly confirmed complete. A hostname association is contextual, no-match is not a safety verdict, and stale/invalid coverage is unknown. The feed has no per-URL confidence, brand, or discovery time. No live OpenPhish refresh or PostgreSQL service migration has been run in this workspace; automated tests use synthetic URLs and mocked requests.
- Website checks inspect a bounded set of authorized response, redirect, TLS, and security-header properties. They are not a full browser audit or exhaustive TLS/cipher assessment.
- NVD CPE/CVE matches are candidates. Applicability requires analyst confirmation; risk remains an academic prioritization policy and is not calibrated without labeled outcomes.
- What-if remediation scores are conditional projections based on saved findings and evidence. They assume only the selected finding is resolved and do not verify real-world changes; a follow-up investigation is needed before saved risk can change.
- Remediation plans and control mappings are analyst-managed workflow records. The local catalog is intentionally small, mapping rationale/confidence are not independently validated, and a saved evidence reference alone does not establish broad control effectiveness or certification. Validation requires an evidence snapshot tied to the relevant investigation; verification of actual production state still depends on the recorded evidence and analyst review.
- ATT&CK support is a small local Enterprise subset with conservative contextual suggestions. It is not a full ATT&CK feed, detection-coverage assessment, attribution system, or proof of adversary behavior. Analyst review is required; relationships without a supported rule remain unmapped.
- Threat-model likelihood, business-impact, confidence, assumptions, and scenario links are analyst inputs. The displayed 1–25 product is an uncalibrated business-impact prioritization aid, separate from technical severity and the CyberLens technical risk score; it is not a probability or prediction. Unconfirmed details remain explicit and require analyst review.
- EPSS is an external predictive estimate available only for CVE identifiers. It is not proof of exploitation or compromise, does not affect scoring, and can be missing or stale when FIRST data is unavailable. CyberLens uses the public FIRST API, which is documented as beta; service availability and daily source-data freshness are outside this application's control. A shared Redis cache and local request limit reduce repeated traffic but do not provide a provider SLA.
- Continuous monitoring supports daily and weekly UTC intervals for individually authorized domain/URL assets. The existing dispatcher polls due slots every two seconds, but it is not a calendar scheduler with an SLA or time-zone selection. A delayed dispatcher runs one catch-up occurrence and advances past missed slots. Pause/cancel stop future runs; an already queued/running investigation may finish unless its authorization has expired or been revoked. There are no automatic containment actions or external notifications.
- The audit chain detects ordinary later event edits/deletes and verifies the stored head, but hashes are not an external trust anchor. A privileged database operator able to rewrite the chain, head, and triggers can recalculate it. Evidence/report hashes detect changed stored bytes; they do not prove forensic authenticity, collection provenance, or chain of custody. No external WORM store or signing key is configured.
- Integrity checks cover saved audit rows and saved evidence JSON at check/report time. They do not validate the original collection process, evidence on external systems, report authenticity after download, or independently archived database backups. No external key or independent verifier is provided.
- Live mode filters retained synthetic history from ordinary projections but does not selectively export or physically remove those rows. Keep their original flags and use a verified protected database backup if an offline archive is required; ad-hoc deletes can break evidence, audit, and saved-report relationships.
- Evidence-grounded AI briefings are disabled because there is no supported local model runtime boundary. No external model dependency or provider was added.
- Restore validation currently compares core table counts in a disposable database. It does not test host failure, encryption-at-rest policy, backup retention, cross-version restore compatibility, or recovery time objectives.
- Playwright full workflow coverage is committed for CI. It requires Docker, Chromium, a fresh Demo bootstrap for smoke login, and a running worker. A local run against persistent data may append test users, assets, investigations, cases, and reports.
- The security posture scorecard is a workspace projection, not a calibrated benchmark or external service-health monitor. Findings currently lack an open/closed lifecycle, so open high/critical counts are unavailable and the displayed high/critical number covers latest observations only. Incident durations omit transitions that were not recorded; provider freshness is relative to the chosen range and summarizes saved collector runs. Control mapping counts do not measure control effectiveness or compliance. Data for an empty or unavailable input remains null/explicitly labeled rather than inferred as zero or safe.
- OSV analysis currently supports only analyst-entered npm and PyPI package names plus explicit versions. It does not parse manifests, inspect a website, infer dependencies, upload SBOMs/source/project files, or query other ecosystems. Advisory data can be incomplete, delayed, withdrawn, quota limited, or unavailable; limits produce explicit partial/provider states. Severity stays unknown if OSV does not provide a supported label, and a version match is only a candidate pending analyst applicability confirmation. A same-component CVE alias suppresses duplicate scoring with NVD but both source records are retained. Live upstream behavior was not validated locally; Demo uses one synthetic package/advisory fixture.
- Module 31 release checks used isolated Demo data. Live provider behavior was not checked. The local container scanner could not run because Docker Scout requires an authenticated Docker account, and Trivy is not installed locally; the configured CI supply-chain job has not run in this workspace. The detailed actual run, warnings, benchmark scope, screenshot links, and any browser-test skip are recorded in [test-results.md](test-results.md#module-31-whole-project-debugging-and-release-verification).
- The 2026-10-22 browser suite had one separate Viewer-credential test skipped because credentials were not supplied. It did exercise role differences in the real API/worker workflow test; the other browser route fixtures use mocked API responses. No external provider smoke test was authorized or performed.
- The cold Windows `httpx` benchmark connection to the local HTTPS gateway showed about two seconds per new client, while reused connections and direct API requests were much faster. A loopback diagnostic and curl timing narrowed this to client/address-selection and gateway connection setup, but did not establish the exact OS-level cause. Read the scope and raw results in [benchmarks.md](benchmarks.md#module-31-measured-run).
