# API guide

FastAPI is the source of truth for the `/api/v1` contract. Open the interactive reference at `/docs` on a running local API. OpenAPI is committed at `backend/openapi.json`; TypeScript API types and operation helpers are committed under `frontend/src/generated/`.

## Authentication and request safety

- `GET /api/v1/auth/csrf` sets a CSRF cookie and returns the token used in `X-CSRF-Token` for writes.
- `POST /api/v1/auth/login` verifies the CSRF token, uses shared Redis login throttling, and creates a server-side session cookie.
- `GET /api/v1/auth/me` returns the current user; `POST /api/v1/auth/logout` revokes the session.
- `POST /api/v1/auth/change-password` changes the password and rotates that user's active sessions.
- Account creation, password change, administrator password reset, and Live first-admin bootstrap screen a submitted password with the keyless HIBP Pwned Passwords range API. A confirmed match returns `422`; Live provider unavailability returns `503` with `Retry-After: 15`. Rejected or unavailable screening does not create the account, change the password, or revoke sessions. Login never screens an existing password. The five-character lookup prefix is sent only to the fixed HIBP HTTPS range endpoint and is not persisted or logged.
- Every mutating `/api/v1` request is rejected when the CSRF cookie and header are missing or differ. The API echoes a request ID in `X-Request-ID`.
- Admin-only user operations are under `/api/v1/users`; Viewer read access does not grant write permission.

## Versioned MITRE ATT&CK catalog

- `GET /api/v1/attack/catalog` always reads the active catalog snapshot from PostgreSQL. New mappings are bound server-side to that version. A supplied stale catalog version is rejected so the analyst refreshes before saving. An override validates against the mapping's own saved catalog version and keeps that binding.
- `GET /api/v1/attack/catalog/versions` returns the active version, available/legacy versions, recent sync attempts, retrieval time, immutable source reference, SHA-256, result counts, import state, and safe error summary. Authenticated roles can read this status; only Admins can request synchronization.
- `POST /api/v1/attack/catalog/sync` requires an Admin session and CSRF token, returns `202`, and writes a durable queued record. The dispatcher delivers it to the existing RQ worker using a stable job ID. In Demo mode this route returns `409`; the worker also refuses to fetch if the application is in Demo mode.
- Synchronization is fixed to the official [MITRE `attack-stix-data` repository](https://github.com/mitre-attack/attack-stix-data) and its Enterprise collection. It follows the repository's [machine-readable collection index](https://raw.githubusercontent.com/mitre-attack/attack-stix-data/master/index.json), resolves a GitHub commit, fetches only the versioned Enterprise bundle at that pinned commit, and does not follow redirects or fetch URLs embedded in STIX objects. The safe outbound client enforces DNS pinning, TLS validation, public-address checks, deadlines, and byte limits.
- The bundle is validated and staged before the active version changes in one database transaction. A malformed, incomplete, oversized, failed, or concurrent import leaves the prior active catalog available. Repeated release/checksum imports are recorded as duplicates instead of duplicating version content. Revoked and deprecated objects remain in their catalog snapshot for historical references but are not offered for new mappings.
- Existing mapping rows retain their version and saved technique text. Reports already generated remain byte-for-byte snapshots; later report generation uses the current mapping rows. Suggestions remain contextual and require analyst confirmation; they do not assert that an ATT&CK behavior occurred.
- The bundled legacy subset remains the active local dataset after a clean upgrade, until an Admin explicitly synchronizes a full release. Demo mode and investigations never require live MITRE access. Source attribution preserves the repository's [LICENSE.txt notice](https://github.com/mitre-attack/attack-stix-data/blob/master/LICENSE.txt) and links the [MITRE ATT&CK Terms of Use](https://attack.mitre.org/resources/attack-data-and-tools/).
- The stored SHA-256 is an integrity check over retrieved bundle bytes. It can detect later changes to those bytes, but it is not independent proof that the source was authentic and does not establish forensic authenticity or chain of custody.

## Controlled continuous monitoring

- `POST /api/v1/monitoring` accepts `asset_id`, the exact `authorization_id`, and `cadence: "daily" | "weekly"`. It is Admin/Analyst-only and requires an unexpired, unrevoked website authorization for the same domain or URL asset. The first due time is one day or seven days after creation, in UTC.
- `GET /api/v1/monitoring` supports `asset_id`, `status`, `cadence`, and the stable `page`/`page_size` collection parameters; history uses the same pagination headers. Responses retain their JSON array shape.
- The dispatcher materializes each due slot into a new immutable-in-history investigation, attempt, and normal transactional outbox record. `(schedule_id, scheduled_for)` and investigation uniqueness constraints prevent duplicate occurrence rows; stable RQ attempt IDs keep job redelivery idempotent. If the dispatcher misses multiple intervals, it runs one overdue occurrence and advances to the next future slot rather than submitting a backlog burst.
- `GET /api/v1/monitoring?asset_id=...` lists schedules; `GET /api/v1/monitoring/{id}/history` returns saved runs and the previous completed/partial investigation ID. `GET /api/v1/monitoring/{id}/runs/{run_id}/changes` reuses the existing evidence graph comparison and its new/changed/no-longer-observed/unknown classifications.
- `POST /api/v1/monitoring/{id}/pause` and `/cancel` stop future scheduling. Cancel uses terminal `completed` state. A run already queued/running is allowed to finish, though the worker rechecks the pinned authorization and stops if it has expired or been revoked. Resume is allowed from paused/failed and requires an active authorization; an optional `authorization_id` can select a renewed record for the same website.
- Schedule states are `active`, `paused`, `failed`, and `completed`. Final investigation failure or authorization expiry/revocation moves an active schedule to `failed` with a reason. Admins and Analysts can manage schedules; every write is session/CSRF protected and audited. All authenticated roles can read schedules and run history.
- Each schedule records its creation mode (`demo` or `live`). The dispatcher, history API, and normal schedule list require that mode to match the currently selected application mode, so a saved Demo schedule cannot become an outbound Live check after a mode change.
- Collector outages remain unknown coverage in Change Radar, never proof that a relationship disappeared. Monitoring does not change existing investigations, findings, evidence, risk revisions, or reports. There is no automatic containment or external notification. Demo mode remains offline; explicitly authorized Demo schedules use synthetic collector results.

## Security posture scorecard

- `GET /api/v1/posture/scorecard` requires any authenticated role and accepts `range_days=7`, `30`, `90`, or `365` (default 30). The response includes a generated timestamp, exact UTC window, PostgreSQL source, registered-asset count, investigation count, and data modes.
- Each metric carries `state`, `scope`, `range_days`, `window_start`, `window_end`, and a note. States distinguish available, partial, stale, unavailable, and empty data. A missing numeric score is `null`; unavailable source coverage is never synthesized as a passing or zero-risk result.
- Overall risk is the equal-weighted mean of one latest in-window numeric assessment per asset. Assessment coverage counts expected categories for registered asset kinds (domain/URL: reputation, TLS/web, DNS/email; IP: reputation; email: breach exposure; application: vulnerabilities). Unassessed counts are asset counts per category.
- High/critical observation counts are unique asset/fingerprint pairs in each asset's latest in-window usable investigation, excluding analyst-marked not-applicable records. Because the finding schema has no open/closed lifecycle, `open_high`, `open_critical`, and `open_total` are `null` and `open_counts_available` is `false`; the observed counts must not be interpreted as unresolved findings. Repeated findings are identities observed in at least two in-window investigations.
- Risk and workflow trends use daily buckets through 30 days, weekly through 90 days, and monthly for 365 days. Periods with no saved records are omitted. Incident timings use the cohort of incidents created in the selected range and first recorded `status_changed` events to triaged/resolved/closed; unresolved or unrecorded transitions are pending and not assigned zero duration.
- Provider health summarizes the latest stored collector result per provider across the workspace; freshness is relative to the selected window. It is not a live connectivity or SLA probe. Asset criticality is a current distribution. Security-control coverage uses mappings for latest-observed findings; rejected/not-applicable mappings are excluded, and validated coverage requires a validated mapping with its existing evidence reference. This is not a control-effectiveness or compliance assessment.
- `POST /api/v1/reports/posture` accepts `{"format":"pdf"|"json","range_days":30}` and requires Admin/Analyst plus CSRF. It saves the exact scorecard payload in a new immutable report snapshot. Existing reports are not altered.

Threat-model writes require Admin or Analyst and CSRF/session checks; all authenticated roles can read. `GET /api/v1/threat-model/owners` returns active assignable IDs, usernames, and roles without email fields. Asset context uses explicit `unknown` values until an analyst supplies a classification. Scenario list filters include `asset_id`, `finding_id`, `investigation_id`, `incident_id`, `review_status`, `stride_category`, and `q`, with stable pagination and sort/order parameters. Scenario links must belong to the selected asset, and a linked finding and investigation must share scope. `likelihood` and `business_impact` are integers from 1–5; the response computes `business_impact_score = likelihood × business_impact` on a 1–25 scale. Confidence is separately recorded and excluded from the calculation. The response labels this as business-impact prioritization, not technical severity or the existing technical risk score. `assumptions` and `unconfirmed_information` are analyst-supplied lists. A scenario cannot be marked `confirmed` while unconfirmed information remains.

The local `cyberlens-attack-enterprise-subset-1.0` catalog is a curated subset, not a full ATT&CK feed. Suggestion and mapping reads require authentication; writes require Admin/Analyst and CSRF. A mapping must use a technique ID and tactic in the catalog and cite evidence already linked to its finding or incident. New mappings are proposed and unconfirmed. Analysts can approve, reject, or override a mapping; a review records the actor and timestamp. Curated suggestions are contextual hypotheses and do not establish adversary activity or attribution. An incident classification alone does not imply any technique; unsupported cases remain unmapped.

## Audit and evidence integrity

- `GET /api/v1/integrity` verifies the current audit chain and recomputes saved evidence checksums. `/integrity/audit-chain` returns sequence/link/hash verification details. `/integrity/evidence` is paginated and `/integrity/evidence/{evidence_id}` verifies a single snapshot.
- Integrity states are `verified`, `failed`, `unavailable`, and `incomplete`. No evidence, a missing record, or missing checksum is incomplete; it is not a successful verification. Storage/read errors are unavailable. A checksum mismatch, broken sequence/link, event hash mismatch, or wrong chain head is failed.
- `GET /api/v1/audit-events` retains the existing `details` field and now also returns its `metadata` alias plus `event_sequence`, `previous_hash`, and `current_hash`.
- `GET /api/v1/integrity/audit-export` downloads newline-delimited JSON with the event sequence, hashes, actor, action, entity, timestamp, and metadata. It requires an Admin or Analyst session; the response includes `X-Audit-Chain-State` and `X-Audit-Chain-Last-Sequence` headers.
- New PDF/JSON report snapshots include the audit-chain verification and checksums for evidence referenced by that report. Previously generated report bytes and snapshots are not changed. Checksums can detect subsequent changes to stored content; they do not prove forensic authenticity, who collected the evidence, or chain of custody. No external immutable anchor or signing key is configured.

## Collection pagination

Assets, findings, investigations, incidents, reports, and audit events keep their existing JSON array responses. They accept `page` (one-based), `page_size`, and endpoint-specific filters. Supported sorting is selected with `sort` and `order=asc|desc`; every query includes a stable ID tie breaker. Pagination metadata is returned in `X-Total-Count`, `X-Page`, `X-Page-Size`, and `X-Has-Next` headers. Read the endpoint's generated OpenAPI parameters for its exact filter and allowed sort values.

## Health and metrics

- `/health/live` reports API process liveness.
- `/health/postgres`, `/health/redis`, and `/health/worker` report dependencies independently.
- `/health/ready` requires all three dependencies and includes Demo/Live mode.
- `/metrics` includes request counters and latency summary, queue depth, observed investigation duration, worker heartbeat, and collector/provider status counters. It is an operational snapshot, not a historical time-series backend.

## Vulnerability intelligence

`GET /integrations/nvd/cves` and saved investigation findings expose CVSS (`cvss_version`, `cvss_score`, `cvss_vector`), CISA KEV (`kev`), analyst `applicability`, `evidence_id`, and EPSS as separate fields. Findings include nullable `epss_score`, `epss_percentile`, `epss_observed_at`, `epss_provider_status`, and `epss_freshness`; source score date/provider/cache provenance remains in `details_json` and the investigation evidence snapshot. The score estimates the probability of exploitation in the wild in the next 30 days; percentile ranks the score among scored vulnerabilities. Status values distinguish a score (`success`), no matching score (`no_match`), quota limit, unavailable provider, invalid response, and Demo `not_assessed`. A missing score is not a zero score.

Risk assessment explanation includes `vulnerability_intelligence` records and an explicit EPSS notice. EPSS does not alter the current risk policy. A confirmed applicable CISA KEV finding receives the existing 90-point floor even if its CVSS severity is unavailable. JSON and PDF report snapshots capture CVSS, EPSS, KEV, applicability, risk trace, and their evidence references at report creation; saved report bytes are immutable.

For package analysis, add an explicit `package_ecosystem` (`npm` or `PyPI`) and `package_name` to an application software component. The existing required software `version` is the exact queried version. The fields are optional and paired; when omitted, existing vendor/product/version/CPE inventory and NVD collection continue unchanged. `GET /integrations/status` lists OSV and its current Demo/Live behavior. Investigation findings include an `osv` object with advisory ID, aliases, ecosystem/package/version, affected ranges and version list, fixed versions, references, provider severity metadata, published/modified/withdrawn times, observation time, status/freshness/version, and evidence ID. The same provenance is copied into new investigation/incident JSON and PDF report snapshots.

Live OSV requests follow the official [OSV API reference](https://google.github.io/osv.dev/api/) and [POST /v1/query schema](https://google.github.io/osv.dev/post-v1-query/): they send only `package.ecosystem`, normalized `package.name`, the explicit `version`, and a pagination token returned by OSV. The bounded collector checks at most 20 package rows, three pages per package, 3,000 distinct advisories, and 2 MB per response; reaching a bound is shown as partial coverage. Successful complete results and no-match results use a package-specific six-hour Redis cache and shared request limit. The adapter makes at most one short retry per page for transient connection/timeout/5xx errors; the existing investigation orchestration may schedule its bounded exponential-backoff retry for transient provider evidence. A 429 remains visible as quota limited. Missing/unsupported severity is `unknown`; CVSS vectors are retained as metadata without inventing a numeric score or severity. Withdrawn advisories remain in evidence but do not create candidates. OSV matches are `needs_review`; only an analyst decision of `applies` contributes to risk. Explicit shared CVE aliases are correlated with NVD records only for the same component, while both provider records remain available and one vulnerability contributes at most once.

## What-if remediation simulation

- `GET /api/v1/investigations/{id}/risk/simulation-options` lists only actions supported by an applicable finding, successful collector result, and linked saved evidence. It is read-only and available to authenticated workspace roles.
- `POST /api/v1/investigations/{id}/risk/simulate` accepts `{"action": "...", "finding_id": "..."}` and requires the normal session and CSRF checks. Supported actions are `patch_applicable_cve`, `fix_security_headers`, `replace_expired_or_mismatched_certificate`, `fix_spf_or_dmarc`, `resolve_validated_reputation_finding`, and `resolve_verified_breach_issue`.
- Both routes require a finished investigation. The POST response returns baseline and projected score/band, policy version, category score changes, the affected finding and evidence reference, and the assumptions used. Unsupported action/target pairs or findings without a matching evidence snapshot return `422`; a finding outside the investigation returns `404`.
- The projection passes a filtered in-memory finding list to the same deterministic policy scorer. It assumes the selected issue is fully resolved and excludes only that finding for the scenario. It does not write findings, evidence, risk assessments/revisions, reports, incidents, or playbook tasks. A new investigation is required to verify remediation and update saved risk.

In Live mode, EPSS uses the public FIRST API, a shared Redis six-hour cache, and a per-CyberLens Redis rate limit. It sends no credentials. Demo mode makes no EPSS request and uses fixed synthetic example values. The [FIRST EPSS API](https://api.first.org/epss/) documents the query and response fields; [FIRST's EPSS data description](https://www.first.org/epss/data_stats) defines the probability and percentile fields.

In Demo mode all collector results are synthetic. Live mode does not substitute Demo findings for provider failures. See [architecture](architecture.md) for evidence provenance and authorization boundaries.

## Remediation plans and control mapping

- `GET /api/v1/remediation/controls` returns the locally versioned `cyberlens-controls-1.0` catalog. Controls provide practical objectives and guidance; the catalog is not a certification or compliance decision.
- `GET /api/v1/remediation/plans` supports stable `page`, `page_size`, `status`, `priority`, `finding_id`, `incident_id`, `q`, `sort`, and `order` parameters. A plan response includes actions, mappings for its finding, and saved verification evidence references.
- `POST /api/v1/remediation/plans` creates a plan, optionally linked to a finding, incident, and playbook task. `PATCH /api/v1/remediation/plans/{plan_id}` updates workflow fields. Add child actions with `POST /api/v1/remediation/plans/{plan_id}/actions` and update them with `PATCH /api/v1/remediation/plans/{plan_id}/actions/{action_id}`.
- Map a finding to a catalog control with `POST /api/v1/remediation/findings/{finding_id}/controls`, providing `control_id`, analyst `rationale`, and `confidence` from 0 to 1. Read mappings with `GET` on the same path and update their workflow/evidence with `PATCH /api/v1/remediation/findings/{finding_id}/controls/{mapping_id}`.
- Plans, actions, and mappings use `proposed`, `planned`, `implemented`, `validated`, `rejected`, and `not_applicable`. Validating an action or finding-control mapping requires a saved evidence ID from the linked finding's investigation. When a plan has no finding, verification evidence must belong to its linked incident investigation. This records evidence context; it does not establish broad control effectiveness.
- All reads require authentication. Writes require Admin or Analyst roles and standard CSRF/session checks. Create/update operations emit audit events. Existing findings, risk assessments, and report snapshots are not modified; reports generated after remediation changes include a point-in-time remediation section.

## Optional XposedOrNot community email lookup

- XposedOrNot is independently disabled by default and is never an automatic fallback for HIBP. Set `XPOSEDORNOT_ENABLED=true`, `XPOSEDORNOT_COMMUNITY_USE_ACK=true`, and a private Fernet-compatible `XPOSEDORNOT_CACHE_KEY` only after determining that the deployment's use is permitted. The provider describes community access as personal and low-volume and publishes caps of 2 requests/second, 25/hour, and 100/day per IP. See [provider scope, coverage, privacy, and configuration](xposedornot.md).
- An investigation request selects `email_breach_provider: "xposedornot"` and, in Live mode, must include `xposedornot_authorization_confirmed: true`. The initiating user must be an authenticated Analyst or Admin and confirms the selected address may be sent to XposedOrNot. CyberLens stores a provider- and asset-scoped grant with actor, consent version, 30-day expiry, and revocation; audit metadata excludes the email. No user-supplied provider URL is accepted.
- The external call is one HTTPS GET to the documented basic `check-email` endpoint with the documented optional `details=true`; it does not call the analytics/domain API or a paid service. Response-size, safe-network, timeout, and shared Redis quota/cache controls apply. A provider `429` returns `quota_limited` and is not automatically retried; Redis unavailability fails closed.
- Successful findings retain separate XposedOrNot source/evidence and only explicitly verified records affect the existing historical-exposure policy. Missing verification stays unknown. `no_match` reports “No record found in this provider's dataset.”; unavailable, quota-limited, malformed, and failed requests are distinct and never mean safe. New report snapshots name the provider, status, observation/evidence reference, and coverage limitation. Existing reports are immutable.
- Demo mode allows selecting the synthetic XposedOrNot fixture and never sends an address externally. Automated tests use synthetic addresses and mock all provider requests.

## Shared Spamhaus DROP snapshots

- Authenticated users can read `GET /api/v1/integrations/spamhaus-drop/status`. It reports mode/enablement, active snapshot ID and canonical checksum, parser version, record count, retrieval/provider dates, last successful revalidation, configured freshness, attribution/copyright metadata, and the latest refresh attempt.
- Admins can queue `POST /api/v1/integrations/spamhaus-drop/refresh` with the normal CSRF token. Demo returns `409` and never contacts the provider. Live refresh attempts are deduplicated and the configured minimum interval is 24 hours; an early new request after the active attempt is finished returns `429` with the next allowed time. Only the existing dispatcher/worker performs the download.
- Investigation collector runs expose nullable `feed_snapshot_id`; `GET /api/v1/investigations/{id}` returns that reference with each run. `GET /api/v1/reports/{id}` includes the pinned snapshot, evidence ID, freshness/result, provider date, checksum, attribution, copyright, and matching networks in the report's immutable snapshot.
- The `spamhaus_drop` result checks only a directly submitted public IP against the saved local snapshot. A match creates a medium `needs_review` reputation candidate. It cannot alter risk until an analyst sets applicability to `applies`; stale/missing/checksum-invalid feed data is unknown coverage. No-match means “Not listed in this snapshot.” and does not imply safety.
- Source endpoints are fixed to the official IPv4/IPv6 JSON feeds and use the bounded, DNS-pinned safe HTTP client, TLS verification, no redirects, shared deadline/size limit, and conditional validators. See [operation, scope, and attribution](spamhaus-drop.md).

## CINS Army and IP source history

- Authenticated users can read `GET /api/v1/integrations/cins-army/status`. It returns the source's enabled state, active snapshot ID, canonical checksum, parser version, exact-address count, local retrieval time, last successful revalidation, freshness/age, attribution, latest attempt, and any configured next refresh. The feed does not supply a publication timestamp.
- Admins can request `POST /api/v1/integrations/cins-army/refresh` with CSRF protection. It queues a durable attempt in the shared threat-feed dispatcher/RQ queue and uses the CINS source's own cooldown. The initial CyberLens interval is 24 hours, configurable through `CINS_ARMY_REFRESH_INTERVAL_HOURS` with a 24-hour minimum. This interval does not claim anything about provider publication frequency. Demo mode returns a conflict and makes no network request.
- `GET /api/v1/investigations/{id}` includes `ip_intelligence` for IP assets. Its `sources` array contains independent Spamhaus, CINS Army, and VirusTotal summaries with status, freshness, observation time, evidence ID, and snapshot ID where applicable. `corroboration_label` says `Listed by two sources` only when both feed observations are fresh/synthetic and listed. VirusTotal is never counted as a second list source. The label does not assert statistical independence or increase severity.
- `ip_intelligence.history` classifies valid observations as baseline, newly observed, continuing, no longer listed, or continuing absence. A no-longer-listed classification requires a later successful observation against a different validated snapshot. A stale, failed, missing, or invalid snapshot is `unknown` and cannot create a removal event. Later absence is not proof of remediation.
- New investigation and incident report snapshots retain each feed collector run's snapshot/evidence ID and include the grouped source history. Reports already saved are unchanged. See [CINS feed behavior and limits](cins-army.md).

## Optional OpenPhish community URL feed

- Live collection is disabled by default. Before enabling it, review the [official public feed repository](https://github.com/openphish/public_feed) and [current terms](https://www.openphish.com/terms.html). Community use is limited to the purposes stated by the provider; business/security operations and third-party disclosure require prior written provider permission. `OPENPHISH_USE_ACK=true` records operator acknowledgement only and grants no provider rights.
- Personal-only configuration requires `OPENPHISH_ENABLED=true`, `OPENPHISH_USE_ACK=true`, and an active `OPENPHISH_PERSONAL_OWNER_USERNAME`. In this mode, the backend restricts sign-ins and all authenticated workspace APIs—including findings, evidence, search, history, integrations, incidents, reports, exports, and downloads—to that owner while OpenPhish data is retained. Existing sessions are checked on every request. Disabling the integration does not lift the restriction while the pinned source data remains.
- Shared/business access remains disabled unless prior written permission covers that use and disclosure and the operator separately sets `OPENPHISH_PROVIDER_SHARING_PERMISSION_ACK=true`. That setting is an attestation, not the permission record. Demo uses an offline reserved-domain fixture regardless of Live settings.
- `GET /api/v1/integrations/openphish/status` reports operator configuration, access scope, snapshot identifier/checksum, retrieval/revalidation age, integrity state, and safe refresh status. It never returns indicator rows. `POST /api/v1/integrations/openphish/refresh` is Admin-only, CSRF-protected, and queues into the existing threat-feed dispatcher. Duplicate queued/running requests reuse one attempt; the default 12-hour interval is CyberLens configuration and does not assert provider publication timing.
- The worker downloads only the fixed official feed over the existing bounded DNS-pinned HTTPS client. It validates and atomically activates complete snapshots, preserving the last good snapshot on failure. Investigations only match locally and never submit an asset to OpenPhish or visit any listed destination.
- Matching preserves scheme/hostname normalization and IDNA, exact path case, query, fragment, and encoded reserved characters. A fresh exact hit is “URL listed in OpenPhish snapshot,” medium severity, and `needs_review`; only analyst-confirmed applicability contributes to risk. Same-host matches are contextual and excluded from risk. Stale/invalid snapshots yield unknown coverage. No match means only “No exact URL match in this snapshot.”
- Older URL assets may have lost queries or fragments under historical normalization. They remain unchanged and have `url_retention_complete=false` until an Analyst/Admin confirms the complete saved URL through `POST /api/v1/assets/{asset_id}/url-retention-confirmation`.
