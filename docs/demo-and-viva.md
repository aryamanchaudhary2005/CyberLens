# Demonstration script and viva notes

## Five-minute walkthrough

1. Sign in as the initial `admin` account and change its temporary password.
2. Open **Assets**. Use the seeded `shop.example.test` asset or register one of your own. Explain that demo assets and findings are synthetic.
3. Start the **Routine website** scenario. Open the investigation, show the collector states, evidence checksum, security-header finding, score, and assessed/excluded categories. In **What-if remediation**, simulate fixing the observed header and show the baseline/projected values, category change, evidence reference, and assumptions.
4. Open `Demo customer portal` and start **Vulnerable application**. Show the four synthetic CVE candidates and their initial `needs_review` state. The vulnerability card keeps CVSS, CISA KEV, EPSS, applicability, and evidence separate; the displayed EPSS values are fixed synthetic examples and make no network request.
5. Record a reason and mark the KEV candidate as **Applies**. Show the score change and point out that applicability means inventory relevance; it is not proof of exploitation. Run the **Patch applicable CVE** simulation and explain that its lower projected score is hypothetical; saved findings and reports are unchanged. EPSS is a predictive estimate, not proof of exploitation or compromise, and it does not change the risk score.
6. Create a case from the finding. Move it through triage, response, resolution, and closure. Complete one playbook task, add a timeline note, and enter a resolution summary.
7. Open **Remediation**. Create a plan linked to the finding, case, and a playbook task; add a patch action with verification instructions; and map the vulnerability finding to control SI-2 with a rationale and confidence. Demo evidence is labeled synthetic, so keep the record proposed/planned or describe any validation only as a synthetic workflow example.
8. Download the case PDF and investigation JSON. Show the demo label, report SHA-256, and point-in-time remediation/control snapshot. Existing report snapshots are not rewritten when the plan changes.
9. Open **Evidence graph** on the investigation. Switch between the interactive graph and the accessible relationship list; select an edge to inspect its source, observation time, Live/Demo status, and evidence ID. Compare it with an earlier completed investigation and review the new/changed/no-longer-observed/unknown classifications.
10. Run the **Provider outage** scenario and compare it with a successful earlier investigation. Show that the failed provider's former relationships become **unknown**, never a false removal; other successful collectors can still show confirmed changes.

To demonstrate the package path offline, add an application asset or use `Demo customer portal`, then add a software component with ecosystem `npm`, package name `cyberlens-demo-widget`, and explicit version `1.0.0`. Choose the **Vulnerable application** Demo scenario and run an investigation. The bundled synthetic OSV advisory appears beside the NVD records as a separate `needs_review` candidate with a synthetic provider label, fixed version, alias, and saved evidence reference. No external provider request is made. Other package names/versions do not match this deliberately narrow fixture.

The incident technique matrix in Demo reads the bundled legacy ATT&CK subset. It shows catalog-version metadata, but administrators cannot synchronize while in Demo and opening the page makes no MITRE request. In a separately configured Live-style run, an Admin can queue official Enterprise catalog synchronization; historical mappings keep the catalog version and technique text they were created with. Mapping suggestions remain hypotheses for analyst review and do not claim an ATT&CK behavior occurred. See [catalog synchronization details](api.md#versioned-mitre-attck-catalog).

For the optional OpenPhish workflow, register a URL asset as `https://phishing.example.test/login?campaign=synthetic`, select **URL: OpenPhish exact match** or **URL: OpenPhish and VirusTotal overlap**, and run the investigation. The Demo fixture is synthetic and reserved; it makes no feed or destination request. The result remains `needs_review` until an analyst confirms applicability. The other OpenPhish Demo scenarios show exact no-match and unavailable coverage. Live OpenPhish remains disabled by default and is governed by the personal-use/provider-permission restrictions in [OpenPhish operation](openphish.md).

Reset the synthetic sample records inside the isolated Demo Compose project with `docker compose --project-name cyberlens-demo -f docker-compose.yml -f docker-compose.demo.yml exec api python -m app.cli reset-and-seed-demo`. It only runs when `APP_MODE=demo` and never touches the Live project's volumes.

## Viva talking points

- **Why separate candidate matching from applicability?** Product names and CPE ranges can be ambiguous. A human checks the exact installed version and configuration before the candidate affects vulnerability risk.
- **What does the risk score mean?** It is a deterministic academic prioritization aid using the documented weights, category coverage, severity floors, and applicable KEV rule. It is not a probability or validated industry score.
- **What is EPSS?** It is a separate FIRST estimate and percentile for CVEs. CyberLens records the provider status, observation time, and freshness; an unavailable or missing score stays unknown. EPSS is not proof of exploitation or compromise and does not affect scoring. Applicable KEV findings retain the 90-point floor if CVSS is missing.
- **How is risk history preserved?** Each changed set of findings, collector coverage, and evidence provenance creates an immutable revision under policy `cyberlens-academic-1.0`. Existing PDF/JSON report snapshots are never rewritten. The score card shows the exact contributing findings, source coverage, freshness, excluded categories, rule version, and a weight sensitivity view.
- **Is the score calibrated?** No. CyberLens makes no calibration claim because it does not contain a labeled incident outcome dataset.
- **What does missing coverage mean?** The source could not assess that category. It is shown as excluded, never counted as evidence of safety.
- **What does a breach match say?** An email appeared in historical breach data. It does not establish that the account is currently compromised.
- **How does SSRF protection work?** Every HTTP(S) target and redirect resolves and checks its A/AAAA answers, pins the socket to a validated public address, and shares one cancellable deadline across DNS, connection, and response reads. Private and metadata destinations stay blocked.
- **How are provider credentials and CPE selections constrained?** API keys are sent only to their owning provider origin; authenticated redirects cannot downgrade from HTTPS. A CPE selection must match the inventoried vendor, product, and exact version, and the accepted selection is audited.
- **What is in collector provenance?** Each saved evidence snapshot records the source, provider and version, observation time, freshness state, result status, evidence schema version, and a provider timestamp when available. Website checks also capture redirect hops and TLS/certificate identity details.
- **What do case tasks do?** They capture analyst actions and completion metadata. They do not disable services, reset credentials, or send notifications.
- **How are remediation controls validated?** Plans and actions track analyst work separately from findings and risk. A control mapping has a local catalog version, rationale, and confidence; marking it validated requires a saved evidence snapshot from the same investigation. Synthetic Demo evidence remains labeled and is not a real remediation verification.
- **How are roles and account changes protected?** Viewers can inspect workspace records but cannot write protected records. Admins manage users and roles, cannot deactivate or demote the last active administrator, and password resets revoke the target user's sessions.
- **How is Live website authorization enforced?** A recorded authorization has a finite expiry and can be revoked. The worker checks that it remains active immediately before a website inspection. Existing authorizations receive a 30-day renewal window during migration.
- **What do evidence hashes prove?** They let a reviewer detect changes to the stored evidence bytes. They do not prove who collected the evidence or establish a forensic chain of custody.
- **How is the graph grounded?** Every projected relationship stores a foreign key to the evidence snapshot that supports it, plus source, collector, observation time, and whether it is direct evidence or contextual application linkage. The graph is derived from PostgreSQL records; there is no second graph database.
- **What does change radar do during an outage?** It reports a prior relationship as unknown when its collector failed, was unavailable, was partial, was not applicable, or did not run. Only a successful collector result or a no-match result can support “no longer observed.”
- **What are source limits?** Explicit HIBP email-breach searches require eligible account-search access; password setting uses the separate keyless Pwned Passwords range API. VirusTotal depends on account quota; NVD, CISA, and FIRST EPSS can be unavailable or rate-limited; website inspection is a bounded GET and selected TLS/header observation.
